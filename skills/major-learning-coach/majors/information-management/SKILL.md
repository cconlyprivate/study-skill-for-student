# 信息管理与信息系统（information-management）

> 先读 `../../references/curriculum-rules.md`（难度与排序）与 `../../references/learning-card-template.md`（讲解结构）。
> 本文件只给这个专业的知识骨架与专业习惯。

## 1. 这个专业在训练什么

信管靠三件事吃饭：**把业务规则问清楚**（谁在什么条件下做什么、单据怎么流转）、**把规则落到数据模型与流程里**（表、字段、状态机、权限）、**让它在真实组织里被用起来**（培训、切换、对账、数据有人维护）。缺任何一件，系统都只是演示。

外人最常见的两个误解：一是当它是"写代码不如计科"的二流技术专业，二是当它是"不用懂技术的管理专业"。它的主场是**业务与系统之间的翻译**：一句"库存不足不能出库"，信管要能追问出"哪个仓的库存、在途算不算、锁不锁量、谁有权放行"，再落成一条可测的业务规则。

**最容易误解的一点**：以为核心是软件。核心是**业务规则的完备性与数据的可信度**——上线后最常见的失败不是程序崩了，而是报表口径打架、主数据重号、流程没人按新制度执行。

**最陡的三门课**：信息系统分析与设计（因为要求同时握住业务、数据、流程三套语言）、运筹学（因为要先"翻译"成数学模型，而题目往往不给变量）、数据库原理的范式部分（因为拆分要付出连接代价，没有唯一答案）。

## 3. 能力目标（毕业时能做的可检验的事）

1. 能把一段口述业务整理成含角色、单据、状态与异常流的可验收需求规格。
2. 能对同一业务分别画出泳道流程图、分层 DFD 与 ER 图，并说明三者的对应关系与不一致处。
3. 能把 ER 图转成满足 3NF 的关系模式，写出建表语句与完整性约束，并说明哪里故意留了冗余。
4. 能把一个排产或配货问题写成线性规划模型，求解并解释影子价格与灵敏度区间。
5. 能用混淆矩阵、支持度置信度提升度评价一个挖掘方案，指出它在业务上能不能用。
6. 能为一个系统写出 UAT 用例、切换方案与对账口径，并给出回滚条件。
7. 能为一类核心数据（客户、物料）指定唯一来源、编码规则与质量校验规则。
8. 能对一个现有流程算出周期与等待占比，给出改造方案与量化收益。

## 5. 术语与符号约定

| 符号/术语 | 含义 | 单位/范围 | 本专业容易写错的地方 |
|---|---|---|---|
| 业务流程图（泳道图） | 谁在哪个环节做什么、判定之后走哪条分支、先后顺序 | 一张图一个流程；泳道即角色或部门 | 画成组织架构图；把"系统自动执行"和"人工审批"混在同一泳道；漏掉退回与异常路径 |
| 数据流图 DFD | 数据从哪个外部实体来、经哪个加工、存进哪个数据存储、再流向谁 | 分 0 层与 1 层，加工编号 1、1.1、1.1.1 | 把控制流画进来（箭头写"审核通过后"是流程不是数据）；父子图不平衡；把数据存储画成外部实体 |
| ER 图 | 实体、属性、联系及基数，回答"数据长什么样、之间什么约束" | 一张图一个主题域 | 当流程图画，给联系标时序箭头；M:N 不拆中间表；把可算出的派生属性硬存成字段 |
| 三张图不能互替 | 流程图答顺序与责任，DFD 答数据流向与加工，ER 答结构与约束 | 同一系统三张都要 | 只画一张就交；被问"这个字段在 ER 哪、存进 DFD 哪个存储"时答不上 |
| 1NF / 2NF / 3NF | 属性原子；无部分依赖；无传递依赖 | 目标是消除更新异常 | 把"零冗余"当目标；2NF 只对复合主键有意义，单主键表天然满足 |
| 有意的反范式 | 为读性能或报表固化而保留冗余字段或汇总表 | 每一处都要写维护方案 | 只写"为了快"不写谁维护、何时刷新；冗余字段没人同步，比不建还糟 |
| 瀑布模型适用条件 | 需求稳定、验收标准能提前冻结、变更代价高（合规、硬件、招投标） | 以阶段门与基线控制 | 把"文档多"当瀑布；判据是需求变更频率与可冻结程度，不是文档量 |
| 敏捷 / 迭代适用条件 | 需求边做边清、能持续拿到真实用户、可小步交付验证 | 常见 2–4 周一个迭代 | 把"不写文档"当敏捷；用户不在场时敏捷会退化成随时改需求 |
| 需求获取四法 | 访谈（挖深度）、问卷（铺广度）、跟岗观察（看真实行为）、文档与原型（既有规则与验证） | 至少两法交叉验证 | 只访谈就写规格；人会说错自己怎么做，观察结果与访谈冲突时以单据和系统日志为准 |
| UAT（用户验收测试） | 业务方按验收标准在准生产数据上跑真实业务用例并签认 | 用例逐条来自需求基线 | 让开发自己跑一遍就签字；验收主体错位，等于没验收 |
| 并行切换 | 新旧系统同时运行一段，逐笔对账后再停旧系统 | 通常覆盖一个完整业务周期（如一个月结） | 低估双份录入成本；不设对账口径与退出条件，并行会变成永久 |
| 直接切换 / 试点切换 | 一次性停旧上新 / 先一个部门或地区上线再复制 | 试点要列可复制清单 | 直接切换不留回滚点；试点不写复制条件，只是把问题延期 |
| 数据治理 | 谁对哪类数据负责、按什么标准、怎么考核 | 组织加制度加流程，不是一套工具 | 把治理当成买平台；没有数据 owner 的治理落不了地 |
| 主数据 | 跨系统共享的核心实体：客户、物料、供应商、组织、科目 | 一实体一个权威来源 | 与事务数据混谈；主数据的关键是唯一可信来源加同步机制，不是"存一份全的" |
| 元数据 / 数据标准 | 数据的定义、口径、类型、取值范围与责任人 | 一字段或一指标一条标准 | 只登记字段名不登记口径；"销售额"含不含税不写清，两张报表永远对不上 |
| 线性规划三要素 | 决策变量、目标函数、约束条件 | 变量非负，约束单位与目标一致 | 漏非负约束；把"不超过产能"写成等式；目标与约束混在一句里 |
| 影子价格 / 灵敏度 | 某资源约束右端加 1 单位带来的目标函数增量 | 目标单位每资源单位 | 当成市场价用；只在当前基不变的区间内有效，超出必须重新求解 |
| 起作用约束 / 松弛变量 | 最优解处取等号的约束 / 未用尽的资源量 | 松弛量不小于 0 | 把松弛变量当决策变量答；不起作用的约束影子价格恒为 0 |
| 支持度 / 置信度 / 提升度 | 规则覆盖比例 / 条件成立时结论成立比例 / 相对随机的提升倍数 | 三者都按 0–1 记，提升度大于 1 才算正相关 | 支持度写成百分数又按小数代入；只看置信度高就下结论，忽略提升度小于等于 1 表示无关 |
| 精确率 / 召回率 / F1 | 预测为正里真为正 / 真正例被找出的比例 / 二者调和平均 | 0–1 | 两个分母记反；类别极不平衡时准确率虚高，不能用它选模型 |
| 决策变量下标 | $x_j$ 的 $j$ 按产品、资源或时段编号，从 1 开始 | 与约束编号分开 | 下标串位导致约束写串；多时段模型要写清 $t=1..T$ 与初期库存 |
| 人天 / 人月 | 工作量单位，用于估算与报价 | 1 人月约 21–22 人天，不按 30 算 | 混用而不换算；估算只给单点值不给区间与假设 |
| 基线（baseline） | 通过评审后冻结的需求或设计版本 | 每次变更产生新版本并留痕 | 口头改需求不进基线，验收时既无依据也无追责 |
| 系统边界 | 系统负责什么，什么留给外部组织或系统 | 边界外一律画成外部实体 | 把组织边界当系统边界；边界一错，DFD 与用例全错 |
| 数据字典 | 对数据流、数据存储、加工与数据项的最小定义集合 | 与 DFD 分层一一对应 | 只写名称不写组成与取值；DFD 上每一根箭头都应能在字典里查到 |
| 总拥有成本与回收期 | 软件、实施、培训、数据迁移与并行期人力的合计投入 | 回收期按月或年计 | 只算软件费；收益不写测量口径，立项论证就只是口号 |

## 6. 典型题型与解题套路

### 系统分析设计题（给一段业务口述，要求出需求与方案）
1. 先划系统边界：写清系统负责哪 3 件事、哪 2 件事留给财务、OA 或仓库。边界不定，后面的图与用例全废。
2. 从口述里抽三类东西：单据（候选实体）、状态（待审、已审、已出库）、角色（谁触发）。凡是"如果…就…"的句子，逐条编号成业务规则表。
3. 三张图分工画：泳道图讲顺序与责任、DFD 讲加工与存储、ER 讲结构；再交叉核对——DFD 的每个数据存储都应能在 ER 里找到表，泳道图的每个判定都应有规则编号。
4. 补非功能指标：并发用户数、单据量每天、响应时间、可用性。没有数字就选不出架构。
5. 落到验收与切换：UAT 用例、并行周期、对账口径、回滚条件。
**常见失分点**：只画一张图就交，或三张图各画一套互相对不上（DFD 里有订单表，ER 里找不到）。

### 数据库设计题（ER 到关系模式，再到 SQL）
1. 先写业务句子："一个订单可以有多个明细，一个明细只属于一个订单"，基数从句子读出来，不靠猜。
2. M:N 一律拆中间表，把联系自身的属性（数量、单价、生效日期）放进中间表，不要塞进两端实体。
3. 判范式：先找候选键，再找部分依赖（只对复合主键成立）与传递依赖；每拆一步都写出拆的理由和新增的连接。
4. 若故意反范式，补三件事：冗余字段由谁维护、什么时候刷新、不一致时以谁为准。
5. 落 SQL 并给约束：主键、外键、唯一、非空、检查；再用一条典型报表查询验证索引是否够用。
**常见失分点**：把多对多画成两个一对多；拆完表不给外键，靠"程序里注意"保证一致性。

### 业务流程优化题（现状流程到目标流程）
1. 先把现状画成泳道图，每个活动标处理时间与等待时间；等待占比通常比处理时间更能说明问题。
2. 判增值：客户愿不愿为这一步付钱。审批、转抄、重复录入、跨系统再录一遍，都是典型非增值。
3. 用清除、简化、整合、自动化四类动作逐条改，每条动作注明它消掉的是哪一段等待。
4. 给目标流程与量化收益：周期从几天降到几天、环节数、单据数；同时写清谁的工作量增加，改造最容易忽略执行者。
5. 分清制度改与系统改：制度不改只上系统，等于把纸质审批搬到线上。
**常见失分点**：一上来就写"上系统、上自动化"，既不给现状数据，也说不出省掉哪一步。

### 运筹与数据计算题（LP、运输、关联规则、混淆矩阵）
1. 先定义决策变量并写清单位与下标范围，例如 $x_j$ 表示第 $j$ 个产品在计划期内的产量（件/周）。
2. 写目标前先问最大化还是最小化、单位是什么；再逐条写约束，每条对应一个真实资源或一条真实需求。
3. 解完必须解释：哪几条约束起作用、影子价格多少、资源再加多少就不再有效（灵敏度区间）。
4. 数据题先确认分母：支持度与置信度、精确率与召回率的分母各是什么，再代公式。
5. 结论回到业务语言：不是"最优解 $x=(4,6)$"，而是"每周生产 A 4 件、B 6 件，冲压工时全满，加班 1 小时多赚 15 元"。
**常见失分点**：漏非负约束或把"不超过"写成等式；把支持度当百分数又按小数代入；算完不解释影子价格。

## 7. 常见误区

1. **拿业务流程图当 DFD 用** → 错在混淆"顺序与责任"和"数据加工与存储"；应三张图各画一张，再用"每个数据存储对应哪张表"做交叉检查。
2. **认为范式越高越好** → 错在把零冗余当目标；应按读写比取舍，反范式必须写明维护责任人与刷新时点。
3. **需求只做访谈** → 错在把人说的流程当真实流程；应加跟岗观察与单据抽样，两者冲突时以单据和系统日志为准。
4. **用准确率评价分类模型** → 错在样本不平衡时多数类就能拿高分；应看混淆矩阵、精确率与召回率，并按业务代价定阈值。
5. **UAT 让开发自己跑一遍** → 错在验收主体错位；UAT 必须由业务方按验收标准在准生产数据上执行并逐条签认。
6. **只算软件预算就立项** → 错在漏了实施、培训、数据迁移与并行期双份人力；这三项不列进总拥有成本，回收期一定算错。

## 9. 交叉专业与后续方向

- **和 `计算机科学与技术` 的区别**：计科问"这个算法复杂度多少、系统怎么扛住并发、内核怎么实现"，信管问"这条业务规则该不该进系统、字段归谁、报表口径是什么"。信管**不拼代码深度**：能读懂接口、写得出 SQL 与脚本、看得懂执行计划就够用，编译原理、分布式一致性不是它的考点。
- **和 `工商管理` 的区别**：工商管理问"战略怎么定、组织怎么激励、治理结构怎么搭"，信管问"战略落地要什么数据、流程怎么固化、系统怎么支撑"。信管**不拼管理理论深度**，但必须能把管理语言翻译成可校验的规则与指标。
- **和 `软件工程` 的区别**：软工管"系统怎么分层、变更时动几处、怎么测"，信管管"业务要什么、数据从哪来、上线后谁用"。同一个模块，软工答耦合度，信管答归属部门与口径。
- **和 `统计学` / 数据科学的区别**：统计答"这个估计有没有偏、显著性多少"，信管答"这个模型能不能进业务流程、谁维护特征、结果给谁看"。
- **后续方向**：考研可走管理科学与工程、工商管理下的信息管理方向、图书情报与档案管理；岗位常见业务分析师、产品经理、ERP/CRM 实施顾问、数据分析师、数据治理专员；进阶课程为企业架构、数据仓库与 BI、IT 治理与审计、供应链与运营管理。
