# 软件工程（software-engineering）

> 先读 `../../references/curriculum-rules.md`（难度与排序）与 `../../references/learning-card-template.md`（讲解结构）。
> 本文件只给这个专业的知识骨架与专业习惯。

## 1. 这个专业在训练什么

靠两件事吃饭：**把含糊的需求收敛成可验收的契约**，以及**用可维护的结构和测试把这份契约固定住**。需求一定会变，所以这个专业真正交付的不是"能跑的程序"，而是"改了还不塌的系统"。

外人最常误解它是"写文档的计算机"或"画图的 PM 预科"。文档、用例图、模式、测试，都只是同一个目的的手段：**降低一次变更要触碰的范围**。判断一个软工学生是否合格，看他能不能指着一段代码说清"改这里会连带改哪三处、哪几条测试会红"。

**最容易误解的一点**：以为软工的核心是流程（敏捷/瀑布）。实际上流程只决定节奏，核心是设计质量与测试有效度——流程再对，代码里一个 god class 也救不回来。

**最陡的三门课**：设计（因为要同时握住"现在能跑"与"半年后能改"两个目标）、测试（因为要主动构造别人会犯的错）、软件工程导论（因为抽象且没有唯一答案，靠案例才立得住）。

## 3. 能力目标（毕业时能做的可检验的事）

1. 能把一段口述需求整理成 10 条带验收条件的用例，并画出对应的用例图。
2. 能从用例里的名词导出领域类图，标出每条关联的重数并说明依据。
3. 能对一份 300 行代码标出 5 处高耦合点，给出降耦后的模块边界。
4. 能为一个功能写完单元测试与集成测试，说清哪些依赖用了替身、哪些分支没被覆盖。
5. 能对一个输入域给出等价类表与边界用例，每条用例附可判定的预期结果。
6. 能在测试全绿的前提下做三步重构，每步一个提交且可单独回滚。
7. 能用执行计划判断一条 SQL 是否走索引，并给出改写方案与预期代价。
8. 能写出含环境、复现步骤、预期与实际的最小缺陷报告，让作者一次复现。

## 5. 术语与符号约定

| 符号/术语 | 含义 | 单位/范围 | 本专业容易写错的地方 |
|---|---|---|---|
| 需求 / 设计 / 实现三层文档 | 做什么 / 怎么做（结构与接口）/ 代码 | 三层各有一份基线 | 把设计写进需求，"用 Redis 缓存"是设计决策；需求只写可验收的行为与指标 |
| 用户故事与验收条件 | 用户语言的一句话需求加 Given-When-Then | 一个故事 3 条验收条件 | 把故事当任务卡；没有验收条件的故事不可测，不该进迭代 |
| 需求追踪矩阵 | 需求到设计、代码、测试的对应关系 | 每行一条需求 | 只在评审前补一次；变更时没人更新，矩阵就等于不存在 |
| 用例图 vs 类图 | 用例画参与者与系统的交互目标，类画领域名词的属性与关系 | 用例 5 至 15 个/子系统 | 把功能菜单画成用例（"管理用户"不是用例）；把类图当 ER 图画，丢了行为与可见性 |
| 参与者与系统边界 | 与系统交互的人或外部系统 / 系统负责的范围 | 边界内才画用例 | 把系统内部模块当参与者；边界一画错，整张图都在描述内部调用 |
| `<<include>>` / `<<extend>>` | 必走的公共段 / 可选的分支行为 | 箭头方向：基用例指向被包含者 | 两个关系箭头方向写反；include 是每次必走，extend 是有条件才走 |
| 关联重数 | 一条关联两端各有几个实例 | `1`、`0..1`、`1..*`、`*` | 两端都写 `*` 等于没给约束；重数要能从业务规则里说出依据 |
| 聚合 / 组合 | 整体与部分；组合的部分随整体销毁 | 空心菱形 / 实心菱形 | 把"持有引用"都画成组合；只有同生共死才用实心菱形 |
| 依赖 / 关联 / 泛化 / 实现 | 临时使用 / 长期持有 / 继承 / 实现接口 | 虚线箭头 / 实线 / 空心三角 / 虚线空心三角 | 把 import 一律画成关联；只出现在参数或局部变量里的是依赖 |
| 耦合 | 模块之间的依赖强度 | 7 级，内容到数据，越低越好 | 只说"要低耦合"不给级；答到数据耦合比"尽量解耦"得分高 |
| 内聚 | 模块内部元素的相关程度 | 7 级，偶然到功能，越高越好 | 把内聚与耦合当同义词；二者是两个独立维度，合起来说"高内聚低耦合" |
| SRP 单一职责 | 一个类只有一个变化的原因 | 一条职责/类 | 误记成"一个类只做一件事"；判据是"谁会提这个修改请求"，不是行数 |
| OCP 开闭 | 对扩展开放、对修改关闭 | 靠抽象与多态，不靠分支 | 用"加一个 if/else"冒充扩展；每次扩展都要改老代码就是违反 |
| LSP 里氏替换 | 子类型可替换父类型而不破坏调用方契约 | 前置不加强、后置不减弱 | 最常错在子类抛父类未声明的异常，或悄悄收窄参数范围 |
| ISP 接口隔离 | 客户不被强迫依赖它不用的方法 | 按客户角色拆接口 | 把胖接口拆成十几个单方法接口，制造导航与实现成本 |
| DIP 依赖倒置 | 高层策略与低层细节都依赖抽象 | 依赖箭头指向抽象 | 以为"抽了个接口"就是 DIP；要看依赖方向有没有真的反过来 |
| 设计模式的代价 | 每个模式新增的类、间接层与阅读成本 | 常见 +2 至 +5 个类 | 答题只写模式名不写代价；必须补一句"不用它会怎样" |
| 圈复杂度 | 方法内独立路径数，约等于判定数加一 | 经验阈值每方法不超过 10 | 把它当唯一质量指标；它不惩罚重复代码与命名混乱 |
| 测试金字塔 | 单元、集成、端到端用例的数量比例 | 常见 70/20/10 量级 | 当硬指标背；端到端写得多，通常说明设计不可单测，该回去改设计 |
| 等价类 | 输入域中系统行为相同的子集 | 分有效类与无效类 | 只划有效类；无效类必须单独成用例，和有效值混写会掩盖失败原因 |
| 边界值 | 等价类边界上的取值 | 取 min−1、min、max、max+1 各一次 | 只测 max 不测 max+1；循环体执行 0 次与 1 次同样是边界 |
| 判定覆盖 / 条件覆盖 | 每个判定取真取假各一次 / 每个条件取真取假各一次 | 覆盖率按百分比记 | 把语句覆盖率当证明；语句 100% 仍可能有一半分支没走到 |
| 单元测试边界 | 只测一个类或函数，外部依赖全部替身 | 毫秒级、不碰网络与数据库 | 把"启动了框架上下文再跑"叫单元测试；那是集成测试，慢且随机失败 |
| stub / mock / fake | 预置返回值 / 断言被调用 / 轻量可用实现 | 放在被测边界外侧 | 用 mock 断言内部调用顺序，重构一次测试就红一片 |
| 缺陷 / 故障 / 失效 | 代码里的错 / 被触发的错误状态 / 外部可观察的偏差 | 一条缺陷可对应多个失效 | 三个词混用；报告只写"系统失效"不写触发条件，作者无法定位 |
| 回归测试 / 冒烟测试 | 改完确认旧功能仍正常 / 发布前的最小可用性检查 | 冒烟控制在 10 至 30 分钟 | 认为回归就是全量跑一遍；回归应跟着缺陷走，每个修复配一条 |
| 技术债 | 为赶工期做的设计折中，未来按利息偿还 | 记"利息/人天"与偿还动作 | 把"代码丑"都算技术债；真正的债要能说清利息和该动哪里 |

## 6. 典型题型与解题套路

### 系统设计题（给一段需求，说怎么搭）
1. 先把需求压成四个数字：并发量、数据量、读写比、一致性要求；拿不到就先假设并写在卷面第一行。
2. 画三样东西：模块边界（谁调谁）、关键数据结构（表与缓存键）、失败路径（超时、重试、降级）。
3. 每个决策都写成"选 A，放弃 B，因为约束 C"；只给方案不说放弃项的，一律按没做权衡扣分。
4. 补一段可测试性说明：哪一层可以用单元测试盖住，哪块只能靠集成测试兜底。
5. 收尾给两个上线后能看的指标（如 P99 延迟、错误率），别只画架构图。
**常见失分点**：一上来画微服务拆分，却不写约束与放弃项，评分表里"权衡"整栏空白。

### UML 建模题（用例图、类图、顺序图）
1. 先划系统边界：列出参与者（人、外部系统），明确哪些在被建模的系统内。
2. 用例只写"参与者为了什么目标做什么"的动宾短语，控制 5 到 15 个；公共必走段用 `<<include>>`，可选分支用 `<<extend>>`。
3. 类图从用例的名词里抽类，写属性与方法及可见性符号，再连关联、两端标重数。
4. 顺序图只画一条主流程，用生命线与消息顺序表达，异常流挪到用例规约里。
5. 交卷前自检三条：重数两端是否都写了、聚合与组合是否用对、有没有把缓存队列这类设计决策画进领域模型。
**常见失分点**：用例图画成功能清单（没有参与者和目标）；类图只有名词和属性，没有一个方法。

### 测试用例设计（等价类、边界值、覆盖率）
1. 逐项列出输入的约束（类型、范围、必填、格式、长度），每项单独划有效类与无效类。
2. 每个边界取 min−1、min、max、max+1 四个点，再补空值、超长、特殊字符。
3. 用判定表把条件组合压成最少用例数，并在表里标明每条覆盖了哪个等价类。
4. 每条用例写"预期结果"，必须是可判定的具体值或具体错误码，不写"正常显示"。
5. 最后算语句与分支覆盖率，逐条说明剩余未覆盖分支为什么可以接受。
**常见失分点**：只写输入不写预期；把无效等价类和有效值塞进同一条用例，测试红了也定位不到原因。

### 重构与代码评审
1. 先用一句话定性"坏在哪"：重复代码、过长函数、依恋情结，还是霰弹式修改。
2. 找安全网：有没有测试；没有就先补一条只记录现状的特征测试，再动结构。
3. 小步改：一次只做一种手法（提炼函数、搬移函数、内联），每步跑一次测试。
4. 评审意见分三档：阻断（正确性与安全）、建议（可维护性）、提问（看不懂的地方）。
5. 收尾写清"这次没改什么、为什么"，防止评审范围无限扩大。
**常见失分点**：把重构和改行为塞进同一个提交，出问题时无法二分定位。

## 7. 常见误区

1. **需求文档写成实现说明**（"用 Redis 缓存热点数据"）→ 错在把设计决策提前锁死；应改写成可验收指标，如"热点查询 P99 小于 200ms"。
2. **用例图画成功能清单** → 错在丢了参与者与目标；每个用例都必须能补全"谁、为了什么、做什么"，补不全就不是用例。
3. **以为 SOLID 就是越抽象越好** → 错在只加抽象层不减少依赖；每条原则都要能说出"它防的是哪一种变更"，说不出就是没懂。
4. **单元测试里连数据库和网络一起跑** → 错在把集成测试叫成单元测试；外部依赖一律替身，否则测试从毫秒级变分钟级，还会随机失败。
5. **先写实现再补测试，且只测正常路径** → 错在测试成了实现的镜像；先按等价类列用例表，再写实现，才可能测出漏掉的无效类。
6. **把重构当重写** → 错在没有安全网就大改结构；重构的定义是不改外部行为的小步变换，一次一步、测试常绿。
7. **技术债只记账不排期** → 错在只有清单没有利息和动作；每笔债要写"不还会慢多少/坏在哪"，否则永远排不上优先级。

## 9. 交叉专业与后续方向

- **和 `计算机科学与技术` 的区别**：同一道"订单系统"题，计科答"用哪种结构、复杂度多少、能不能算得动"，软工答"模块怎么切、改一处要动几个文件、哪几条测试会红"。一句话分界：**计科答复杂度，软工答可维护性**。选方向时看你想解释"为什么慢"，还是想解释"为什么改不动"。
- **和 `信息管理与信息系统` 的区别**：信管从业务侧进，答"数据怎么组织、流程怎么落、报表怎么出、主数据谁维护"；软工从结构侧进，答"系统怎么分层、边界在哪、变更时动几处、怎么测"。同一张订单表，信管问"这个字段归哪个部门"，软工问"这张表有几个写入方，加字段会不会连带改三个模块"。
- **和 `数字媒体技术` 的区别**：那边的产出是能直接看到的界面与交互，软工多数时间在看不见的约束里做取舍，交付物是能长期维护的结构。
- **后续方向**：软件体系结构、DevOps 与持续交付、测试开发、技术管理；考研常走软件工程或计算机技术（专硕），复试爱追问设计取舍与项目里的失败决策。
