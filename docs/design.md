# 设计说明

记录三条主要取舍，以及它们各自解决了什么问题、付出了什么代价。

## 1. 为什么是「路由 + 子 skill」，而不是一个大文件

59 个专业，每个专业至少 20 个知识点、20 条术语、3 类题型套路。如果全部写进 `SKILL.md`：

- 粗估 59 × 300 行 ≈ 1.8 万行，约 30–40 万 token，任何客户端都装不下；
- 就算装得下，模型在长上下文里的注意力会被稀释，回答质量反而下降；
- 改一个专业的措辞要动全仓库唯一的文件，冲突率极高。

所以采用三层加载：

```
第 1 层  frontmatter（name + description）      ~80 token  常驻
第 2 层  SKILL.md（路由 + 协议）                ~2k token  触发时
第 3 层  majors/<slug>/SKILL.md（专业内容）      ~3k token  命中专业时
         references/*.md（按模式取一个）          ~1–2k token
```

代价：路由必须准。路由错了，用户会拿到隔壁专业的方法论。所以 `major-index.md` 里维护了别名表和 12 组「容易混淆」，并要求"命中多个就给候选让用户挑"，而不是猜。

## 2. 为什么是「先修图 + 难度分带」，而不是章节顺序

教材顺序是**作者的讲法**，不是**你的学法**。典型问题：教材第 3 章要用第 7 章的定理（作者假设你学过），或者第 2 章第一节其实是全书最难的概念。

本仓库把每个专业的知识点组织成有向无环图，再按三步排序：

1. 按难度分带（L1 → L2 → L3）：先拿到"我能学会"的反馈；
2. 带内按拓扑序：不违反先修；
3. 同层按被依赖次数降序：地基先学。

这就是"从简到难"的可执行定义——**换个人来排，得到同一条路径**。这条性质很重要：如果排序依赖模型当场发挥，用户两次问会拿到两条不同的路，进度就没法记。

代价：给 59 个专业标注前置关系，工作量远大于抄目录。所以 `validate.py` 会检查环、检查入口点、检查是否至少有一条 3 层深的链。

## 3. 为什么默认「引导式」，而不是直接给答案

用户的真实目标是"下次自己会做"，不是"这次交上去"。直接给完整解答会让进度条看起来走得更快，但：

- 用户没有经历"卡住 → 想出"的过程，迁移不了；
- 模型无法判断用户到底哪里不会，下一轮还是从零讲；
- 作业/考试场景下，直接给答案会把工具变成代写。

所以 `solve` 模式固定走：**解题地图（只给步骤名）→ 只展开第一步 → 追问 → 卡住才给提示 → 再卡才给这一步的做法**。用户明确要全解时给，但要标注"参考解"并附一道变式。

代价：急性子的用户会觉得啰嗦。缓解办法是"用户明确说'直接给过程'"时不再坚持——尊重用户比坚持方法论重要。

## 4. 其他决定

- **不自动升档**：连续 3 个点自测全对才升，且要口头告知。自动升档会让用户在不该加速的时候被推着走。
- **进度存本地文件而不是对话记忆**：对话会被清空，文件不会。同时默认写在当前目录（`.major-coach/`），方便学习小组把进度一起提交。
- **`majors/_template` 以 `_` 开头**：校验脚本会跳过它，但它必须能在仓库里被复制。
- **中文正文 + 英文 slug**：中文是主要读者语言；slug 用英文是为了跨平台（Windows 路径长度、GitHub 链接、URL 编码）。

## 已知局限

1. **深度不均**：59 个专业的知识点表是骨架，不是教材。偏门专业的术语表可能不够细。
2. **教材版本会过时**：所有书单只给公认书目，不给页码，就是为了避免版本漂移后的错误引用。
3. **判级只能近似**：5 道题测不出真实水平，它测的是"有没有明显缺口"。所以判级后必须让用户确认。
4. **地区与院校差异**：同一专业在不同学校的课程顺序不同（比如"算法"有的在大二下、有的在大三上）。知识点表按"能力依赖"排，不按学期排，正是为了绕开这个差异。
5. **不覆盖研究生专业课**：目前以本科培养方案为基准。

## 后续可能的方向

- 增加「院校培养方案对照」：同一专业给出 2–3 种常见课程顺序。
- 增加「错题本」：把 `struggling` 聚合成一份可导出的复习清单。
- 让 `validate.py` 检查术语表与本专业知识点名称的一致性（目前只查结构，不查语义）。
